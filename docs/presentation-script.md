## 第 2 页：原始参考实现的问题

### 页面结论

参考实现正确，但热路径存在重复计算、乘零、大块内存流量和较差缓存局部性。

### 四个问题，按“是什么、为什么慢、如何发现”讲

#### 1. 每帧重复准备 FFT

**现象**

原实现每处理一帧，都会重新分配中间数组、重新计算位反转，并在每一级 FFT
蝶形中重新调用 `cos`、`sin` 生成 twiddle。

**为什么慢**

默认用例约有 19 万帧。位反转和 twiddle 只与 `n_fft` 有关，与音频内容无关，
本来只需要在程序启动时计算一次，却被重复了 19 万次。

**怎么发现**

阅读 `src/melspec.cpp` 的 `compute_rfft` 和 `fft_inplace`，可以看到这些分配和
三角函数都位于逐帧循环内部。

**HPC 知识点**

这是“循环不变量外提”和“plan 复用”。高性能 FFT 库通常会先创建一个计划，
把索引、旋转因子和资源准备从热循环中移出去。

#### 2. 实数输入仍做全长度复数 FFT

**现象**

输入帧所有虚部都是 0，但程序仍分配 `n_fft` 个复数，执行完整长度的复数 FFT。

**为什么慢**

实序列满足共轭对称性：

```text
X[N-k] = conj(X[k])
```

负频率一半是冗余信息。利用这个结构，可以把核心复数 FFT 从 `n_fft` 点降到
`n_fft/2` 点。

**怎么发现**

这是由输入类型直接推出的优化。看到 `vector<complex<double>>` 处理实数 PCM，
就应该先问：实 FFT 的共轭对称性是否被利用了？

**HPC 知识点**

算法结构优化优先于指令优化。先减少需要完成的数学工作，再考虑 SIMD 和线程。

#### 3. 稠密 Mel 投影包含大量乘零

**现象**

原实现对 `n_mels × (n_fft/2+1)` 的二维区域进行扫描，但每个三角滤波器只在很窄
的频率范围内有非零权重。

**为什么慢**

稠密投影的复杂度约为：

```text
O(n_mels × n_bins × n_frames)
```

大量乘法的权重是 0，却仍需要读权重、读功率谱并执行乘加。算术量和访存量都被
无意义地放大。

**怎么发现**

观察 Mel 三角滤波器的形状即可确认它是局部支撑。短样本中只改变 `n_mels`，
从 1 增加到 256 时投影时间持续增加，也支持“大量工作是乘零”的判断。

**HPC 知识点**

稀疏计算、有效浮点运算占比和 Arithmetic Intensity。快速程序应尽量让每次
访存服务于非零计算。

#### 4. 完整 double 功率谱过大，且跨行访问

**现象**

default 用例的功率谱形状约为 `[4097, 192397]`。保存 double 需要约 `6.3 GB`。

**为什么慢**

完整矩阵远大于缓存，数据最终只能落到主存甚至 swap。原布局是 `power[k][t]`，
固定一帧并增加频点时，访问会跳过整行，缓存行命中率低。

**怎么发现**

由形状和数据类型可以直接估算内存：

```text
4097 × 192397 × 8 bytes ≈ 6.3 GB
```

再结合代码中的二维数组访问顺序，可以判断存在严重的缓存局部性问题。

**HPC 知识点**

工作集、缓存层次、空间局部性和数据布局。优化内存流量通常比单纯增加算术吞吐
更有效。

### 效果

同口径 1M default 前缀上，原实现为 `61.663 s`，exp001 为 `0.084 s`，加速
`731.206x`。

“所以问题不是测试脚本，也不是磁盘读取，而是每帧热路径里的算法冗余和内存
流量。下一张就进入 exp001。”

## 第 3 页：exp001 的算法优化

### 总体思路

exp001 先不做线程堆叠，而是按以下顺序优化：

1. 复用不随帧变化的数据；
2. 利用实信号结构把 FFT 长度减半；
3. 利用 Mel 滤波器稀疏性删除乘零；
4. 分块融合，避免完整功率谱；
5. 在数据布局正确后使用 SIMD；
6. 最后做 OpenMP 帧级并行。

### 优化 1：预计算并复用 FFT plan

**过程**

- 启动时生成位反转索引；
- 预计算每一级蝶形的 twiddle；
- 把 twiddle 按连续布局存储；
- 每个线程准备一个固定工作区。

**效果**

每帧不再重复分配内存，也不再重复计算相同三角函数。

**为什么这么做**

这部分工作的输入只有 `n_fft`，与 PCM 内容无关，是典型的循环不变量。

**HPC 知识点**

预计算、资源复用、固定工作区和热循环去分配。

### 优化 2：打包半长度实数 FFT

**过程**

把偶数样本和奇数样本打包到复数的实部和虚部：

```text
z[n] = x[2n] / 2 + i x[2n+1] / 2
```

对长度为 `n_fft/2` 的 `z` 做复数 FFT，然后利用共轭对称关系恢复原始实 FFT 的
非负频点。

**效果**

8192 点原 FFT 的核心复数变换变为 4096 点，蝶形、twiddle 和工作区都近似减半。

**为什么这么做**

实序列 FFT 的一半频点是共轭镜像，不需要重复存储和计算。

**HPC 知识点**

算法复杂度、共轭对称性、half-complex FFT 和从数学结构减少工作量。

### 优化 3：稀疏 Mel 滤波器

**过程**

每个滤波器只保存：

- 起始频点；
- 连续非零权重数；
- 权重在扁平数组中的位置。

计算时只遍历三角滤波器的非零区间。

**效果**

投影从“全表扫描”变为与非零权重数量成正比。公式、边界和 Slaney 面积归一化
保持不变。

**为什么这么做**

三角滤波器天然稀疏，零权重不可能贡献结果。

**HPC 知识点**

稀疏表示、只读共享表和有效工作集。保留连续区间，避免通用稀疏矩阵的间接索引。

### 优化 4：256 帧分块融合

**过程**

每 256 帧组成一个 tile：

1. 在 tile 内并行计算 FFT；
2. 当前帧立即计算功率；
3. 立即做稀疏 Mel 点积；
4. 写入较小的 Mel tile；
5. tile 完成后，按 Mel 行连续复制到最终输出。

完整功率谱不再保存到最终矩阵。

**效果**

GB 级完整功率谱被替换成每线程的小块工作区，显著降低内存占用和缓存压力。

**为什么这么做**

后续只消费当前帧功率谱，没有理由保留所有帧的所有频点。分块还能让中间结果
留在缓存中。

**HPC 知识点**

循环融合、分块、工作集、缓存局部性和数据依赖分析。

### 优化 5：SIMD、FMA 和 SoA

**过程**

- 实部和虚部使用两个连续数组；
- 使用 `__restrict` 声明不重叠；
- 强制向量化 FFT 蝶形和 Mel 点积；
- 用 `-march=native` 启用本机 AVX2/AVX-512 和 FMA。

**效果**

单线程完整默认形状的测试中，仅强制向量化就带来约 13% 改善。

**为什么这么做**

先解决算法和内存浪费，再让编译器用更宽的寄存器并行处理多个独立元素。

**HPC 知识点**

SIMD、FMA、数据依赖和自动向量化。向量化无法弥补算法级冗余。

### 优化 6：OpenMP 帧级并行

**过程**

- 同一 tile 内的帧彼此独立；
- 每个线程获得连续帧段；
- 每个线程复用独立 FFT 工作区；
- 一个 tile 只创建一个 parallel region；
- 计算结束后一次 barrier，再按输出行并行复制。

**效果**

64 线程 spread 下四用例合计 `3.777 s`。相比单线程 `79.120 s` 提升约
`20.95x`。

**为什么不是 64x**

读取、写入、线程启动、barrier、共享内存带宽和负载不均构成不可忽略的串行或
共享部分。Amdahl 定律限制了总加速比。

**HPC 知识点**

数据并行、线程绑定、负载均衡、fork/join、barrier、false sharing 和强扩展性。

### 这页的收束语

“exp001 的价值不只是把时间从 79 秒降到 3.8 秒，更重要的是建立了后续单节点和
多节点共用的数学基础。”

## 第 6 页：exp008 单节点最终方案

### 怎么想到

exp007 profile 显示，exp001 default 中：

- 读取与归一化约 `0.20 s`；
- 计算约 `0.49–0.51 s`；
- double 转 float32 与输出约 `0.23–0.25 s`；
- 峰值 RSS 约 `779 MB`。

继续优化 FFT 的收益有限，数据准备、完整 double 输出和转换仍有较大固定成本。
于是 exp008 保留数学，只重做数据生命周期。

### 从 exp001 到 exp008 改了什么

| exp001 的额外成本 | exp008 的改法 |
|---|---|
| PCM 归一化串行 | 用 64 线程 OpenMP 并行归一化 |
| 每个 256 帧 tile 单独创建并行区 | 一个 OpenMP 区域覆盖全部帧 |
| 保留完整 double Mel 输出矩阵 | 每个线程完成 Mel 后直接写 float32 |
| 保留 double tile staging | 删除 staging 中间矩阵 |
| 最后再做串行 double 到 float32 转换 | 删除末遍转换 |

### 为什么这么做

- 归一化是逐元素独立计算，适合数据并行；
- 反复创建 parallel region 和 barrier 有固定成本；
- 题目最终只需 float32 输出，完整 double 输出矩阵没有后续消费者；
- 中间矩阵越小，缓存工作集和峰值内存越低。

### 效果

exp008 default profile：

```text
读取 0.06 s + 并行归一化 0.11 s + 计算 0.36 s + 写入 0.08 s
```

- 峰值 RSS：约 `779 MB` 降至 `394 MB`；
- 四用例：`3.777 s` 降至 `2.733 s`；
- 相对 exp001：`1.382x`；
- 1M default 相对原实现：`1427.391x`；
- 正确性：`4/4 PASS`。

### HPC 知识点

数据流和内存生命周期优化、减少 barrier、避免不必要的中间表示、并行归一化、
峰值内存和缓存工作集。

## 第 7 页：单节点到多节点

### 为什么自然想到多节点

exp008 已把单节点内部的数据路径缩短，剩余成本开始转向总帧规模和完整输出。
按连续帧区间把工作拆给多个节点，是继续利用帧级独立性的直接方法。

### 演进过程

```text
exp001 单节点：3.777 s
exp004 两节点旧路径：3.083 s
exp004 三节点旧路径：2.533 s
exp009 三节点最终：2.186 s
```

两节点旧路径比 exp008 慢，说明“增加节点”不是自动收益。启动、协调、读取和
写入路径必须一起优化。

### exp009 的实现

1. 每个 rank 只读取自己负责的连续 PCM 帧区间；
2. 每个 rank 在本地并行归一化；
3. 使用 exp008 的单 OpenMP 区域直接计算 float32；
4. rank 0 准备共享输出并写入每轮 64-bit token；
5. 其他 rank 用 `pread` 确认 token；
6. 各 rank 直接 `pwrite` 不重叠输出列；
7. 不需要 Gather，也不需要把所有结果交给 rank 0。

### 为什么不用原来的 MPI Gather

MPI 功能路径能正确工作，但短用例的 `MPI_Init`、启动和 Gather 固定成本较高。
原生 Slurm 多进程直接利用 rank 环境变量和共享文件系统，避免不必要的启动协议
和汇总步骤。

### 效果

- 四用例合计 `2.186 s`；
- 相对 exp001 `1.728x`；
- 相对 exp004 `1.159x`；
- 四个单用例均为当前最低；
- `4/4 PASS`。

### 对应 HPC 知识点

SPMD、局部数据划分、进程与线程混合并行、进程启动成本、通信规避、共享文件
系统并发 I/O、token 同步和弱扩展性。

## 第 9 页：GPU 与 CPU+GPU 为什么没有胜出

### 先给结论

GPU 算术不慢。失败的是完整 CLI 的端到端效率，主要损失在固定启动、设备传输、
stream 同步和共享输出 I/O。

### GPU 路线结果

| 方案 | 四用例合计 |
|---|---:|
| exp006 两节点纯 GPU | 4.024 s |
| exp002 单节点双 GPU | 5.164 s |
| exp005 两节点 CPU+GPU | 5.179 s |
| exp003 单节点 CPU+GPU | 5.207 s |

### exp006 default profile

| 阶段 | rank 0 | rank 1 |
|---|---:|---:|
| 本地 PCM 读取 | 0.093 s | 0.093 s |
| CUDA 初始化和 plan | 0.060 s | 0.056 s |
| H2D、kernel、D2H、同步 | 0.161 s | 0.233 s |
| 共享输出写入 | 0.280 s | 0.489 s |

### 为什么不是磁盘输入导致

输入读取约 `0.093 s/rank`，只占阶段时间约 9%。default 完整输出约 188 MiB，
rank 1 的共享写入约占总阶段时间 49%。

### 为什么 GPU 没有赢

1. 每 1024 帧同步一次，default 每 rank 约 94 次；
2. D2H 使用 pageable 缓冲，无法与下一批计算充分重叠；
3. CUDA 初始化、显存分配和 cuFFT plan 对短用例是固定成本；
4. 完整输出最终仍要写入共享文件系统；
5. CPU 路线已经使用实数 FFT、稀疏 Mel、SIMD 和 64 核 OpenMP。

### 为什么 CPU+GPU 反而更慢

CPU 和 GPU 共享主机内存、缓存和 I/O。把一部分帧分给 CPU 后，wall time 仍由
较慢的一侧和尾部延迟决定。exp003 调参中，纯 GPU 约为 `5.102 s`，加入 CPU
分担后没有形成有效加速。

### 如果继续优化 GPU

优先方向是：

- pinned host memory；
- 双缓冲；
- 异步 D2H；
- 下一 tile 的 GPU 计算与上一 tile 的写盘重叠；
- 减少 stream 同步频率。

### HPC 知识点

端到端性能、kernel 之外的固定开销、PCIe 传输、异步执行、Roofline/Arithmetic
Intensity、资源竞争和尾部延迟。

## Q&A 速查

### 1. 为什么原始实现这么慢？

每帧重复 FFT 准备、实数输入做全长度复数 FFT、Mel 全表乘零，并保存约 6.3 GB
的完整 double 功率谱。

### 2. exp001 最关键的优化是什么？

打包实数 FFT 和稀疏 Mel 是算法层核心。前者把 FFT 长度减半，后者删除大部分
零权重乘法。

### 3. 为什么先优化算法，再做 SIMD 和 OpenMP？

SIMD 和线程只能加速有效工作。如果一半计算是乘零或重复准备，并行只会更快地
完成浪费。

### 4. exp008 相比 exp001 改了什么？

保留 FFT/Mel 数学，只改数据路径：并行归一化、单 OpenMP 区域、直接 float32
输出，删除 double 输出矩阵、staging 和末遍转换。

### 5. 为什么 exp008 的峰值内存从 779 MB 降到 394 MB？

删除了完整 double Mel 输出和 double tile staging，只保留线程工作区和最终
float32 输出。

### 6. 为什么单节点会自然过渡到多节点？

exp008 后剩余成本转向总帧规模和完整输出。帧之间基本独立，适合按连续帧区间
做 SPMD 分布。

### 7. 为什么两节点旧版反而比单节点慢？

节点增加会带来启动、协调、读取和写入成本。旧数据路径没有同时优化，收益被
固定开销抵消。

### 8. exp009 为什么不使用 Gather？

每个 rank 已经拥有最终矩阵的不重叠帧列，直接 `pwrite` 可以消除汇总通信和
rank 0 瓶颈。

### 9. token 协调解决什么问题？

避免 rank 读到上一轮的 ready 状态。每轮写入新的 64-bit token，确保所有 rank
只写当前作业的共享输出。

### 10. GPU 为什么没有赢？

kernel 算术很快，但完整 CLI 还要承担 CUDA 初始化、H2D/D2H、每次 1024 帧的
同步、pageable 缓冲和共享输出写入。

### 11. GPU 有没有计算瓶颈？

没有看到 kernel 计算成为主因。exp006 的 GPU 路径约 `0.161–0.233 s`，而输出
写盘可达 `0.489 s`。

### 12. 为什么 CPU+GPU 没有超过纯 GPU？

两侧共享内存、缓存和 I/O，最终 wall time 由较慢一侧和尾部决定。分工增加了
协调和资源竞争。

### 13. 1M 加速为什么不是官方主结论？

1M 对照只用于原实现速度比较。官方四用例覆盖四种参数组合，并经过完整容差
检查，因此主结论使用 `3.777 / 2.733 / 2.186 s` 和相对值 `1.382x / 1.728x`。

### 14. 为什么使用 double 计算但输出 float32？

double 累加保留了跨 FFT、功率和 Mel 的数值稳定性，题目的最终输出格式是
float32。只在写入时转换，既满足语义，又减少最终存储。

### 15. 如何证明没有为了速度牺牲正确性？

两个最终方案都通过官方 `4/4 PASS`；数值门限为 `rtol=1e-3`、`atol=1e-4`；
正式测量来自 Slurm 三次运行最小值；原始日志、机器可读结果和实现源码均保留。

### 16. 为什么没有直接使用 FFTW 或 oneMKL？

当前方案优先选择可解释、可移植的实现。科学库可以在相同输入和容差下继续评估，
但必须保持普通构建入口、数值语义和可复现实验。
